# SkillHub audit and roadmap

**Reviewed 12 November 2026 · repository HEAD `208a1be` · Windows desktop and local daemon**

## Executive assessment

SkillHub addresses a real workflow problem. A shared, portable skill library plus provider adapters and a local MCP entry point is a coherent product. The present implementation gives a reassuring impression of sync while treating different copies, edits, and deletions as if they were interchangeable. The most important defect is that **turning off sync for one provider can delete the canonical skill and its other copies**. Removing one bundled file can take the same path. The app also accepts supporting-file paths that escape the skill folder, and its optional public tunnel forwards unauthenticated REST routes that can exercise that write path. Its configuration repair can remove unrelated TOML tables.

**Release decision** · Hold public distribution. Fix containment, deletion semantics, config integrity, and the public network boundary before inviting outside users or performing further UI polish. Fix the document and import flows before claiming that the desktop app is ready for daily use. The existing test suite passed **12 of 12** tests. Independent fixtures reproduced the data-loss, path-containment, config corruption, and interface failures below.

## 1. Desktop UX and frontend state

### 1.1 Library and navigation

**UI-01 · P1 · Docked library can lose its entire result area.** At 1280 × 820 the first card began at y=321. At 460 × 500, it began at y=469, leaving about 31 visible pixels. Opening Filters & Tags put the first card at y=1118 and clipped most drawer controls. The outer application and Library hide overflow, the header is non-shrinking, and only the grid area scrolls. A header that can grow with dozens of tags needs either a bounded independent region or a place in the primary scroll. The native minimum is 460 × 500 for the *whole form*, including chrome. The tested web viewport is therefore already a generous approximation of minimum size. Evidence [layout.css, 5–12 and 87–130](src/SkillSync.Daemon/wwwroot/css/layout.css#L87), [components.css, 319–378 and 1999–2128](src/SkillSync.Daemon/wwwroot/css/components.css#L319), [SkillHubDesktopShell.cs, 104–109](src/SkillSync.Daemon/Desktop/SkillHubDesktopShell.cs#L104).

**UI-02 · P2 · The chrome spends three rows describing the same collection.** The top bar prioritizes brand, a provider popover, Explore, New, theme, and Settings on every screen. Library adds a full-width search, category buttons with counts, then a second set of clickable categories with different names, order, and counts, plus a total and a prose restatement. “My Skills” becomes “Personal,” “Active & Synced” becomes “Live & Synced,” and System moves after Plugin Catalog. The collection total also sits beside overlapping counts. Search changes the first row’s counts while the second row stays global. Both look like the result count. The visual issue is allocation of space and attention. The user needs a location, a query, a count for the displayed results, and one obvious next action. Evidence [index.html, 17–217](src/SkillSync.Daemon/wwwroot/index.html#L17), [skillList.js, 111–185](src/SkillSync.Daemon/wwwroot/js/components/skillList.js#L111).

**UI-03 · P1 · “Synced” is a false positive.** A fixture with all four switches off still showed a green “Synced” pill and appeared in Active & Synced. The frontend defines the category as any noncatalog, nonsystem record. The REST listing requires at least one enabled flag for that category, regardless of installation or disk result. MCP status counts even all-disabled skills. Settings and the provider popover treat directory detection as a connected provider and count enabled intent as completed writes. A pulse and reassuring copy amplify an unsupported claim. Model three separate facts per target: configured intent, available destination, and verified deployment with last result. Evidence [skillList.js, 71–76, 125–137, 626–638, 706–746](src/SkillSync.Daemon/wwwroot/js/components/skillList.js#L71), [statusBar.js, 104–189](src/SkillSync.Daemon/wwwroot/js/components/statusBar.js#L104), [SyncEngine.cs, 92–119](src/SkillSync.Daemon/Core/Engine/SyncEngine.cs#L92), [McpJsonRpcHandler.cs, 607–636](src/SkillSync.Daemon/Mcp/McpJsonRpcHandler.cs#L607).

**UI-04 · P1 · The tag scope is a hidden navigation override.** All Skills starts as the default. Selecting a tag bypasses the active category while that category stays highlighted. Category or stat-button clicks retain the tag and usually keep returning the same cross-category results. Switching to Current Tab retains a now-invisible tag. The “smart auto-switch” branch inside chip selection is unreachable in normal Current Tab use because the renderer removed chips with zero current matches. System visibility and reserved tags change with the current tab even in global scope. Origin choices are derived from presentation labels, capped at six, and counted before applying search or tags. A selected origin can survive a scope change while its chip disappears. The active indicator is a passive span and there is no general Clear Filters action. Empty-state suggestions ignore portions of the current filter and can report “other tabs” when the matches are simply hidden by origin. Evidence [skillList.js, 173–198, 316–451, 467–600, 801–827](src/SkillSync.Daemon/wwwroot/js/components/skillList.js#L316).

**UI-05 · P1 · Tag management mixes durable mutations and browser-only labels.** Creating a tag in the drawer writes local storage, so MCP and fresh WebView profiles cannot see an unassigned tag. Assigning a tag in a draft can register it before save. Editor input ignores the normalized return value, making `Release Notes` produce different tag identities in the store and skill. Reader input can also assign reserved tags after the local-store helper rejects them. Rename validates the new slug only superficially before calling the backend, including reserved names the local-store helper will reject afterward. The manage panel counts catalog tags alongside editable skills, replaces its entire DOM on refresh, and can destroy an in-progress rename. Source category and count behavior differ between surfaces. **UI-06 · P2 · Skill cards compete for attention and are difficult to operate by keyboard.** A typical personal card contains two badges, description, a single-line lightning treatment, tags, and up to four provider pills. ## 2. Sync engine, storage, and provider compatibility

### 2.1 Destructive operations and consistency

**SYNC-01 · P0 · Provider disable and supporting-file deletion propagate as global deletes. Reproduced.** Start watchers, save a fixture with `scripts/helper.txt` and a second bundled file, and remove just the first file from Gemini. The resolver returns the skill slug for a supporting path. The timer sees the deleted path is absent and sends `Deleted`. The engine handles deletion before reading the primary file and removes the canonical skill and all computed destinations. Separately, turning Gemini off deletes the projected directory. Its own watcher sends a delete back to the engine. The raw hash guard handles writes only. No operation or ownership check distinguishes the daemon’s removal, a one-provider removal, a bundle file removal, and explicit library deletion. Gemini’s canonical copy disappeared in both fixture runs. User-driven delete also recursively deletes computed folders without requiring an owned file manifest, including files SkillHub never created. Failures are swallowed after dropping the ledger record, and success is published. If a directory survives, startup can adopt the remainder again. Evidence [MultiRootFileWatcher.cs, 105–119, 174–254](src/SkillSync.Daemon/Watchers/MultiRootFileWatcher.cs#L174), [ProviderDiscoveryService.cs, 540–576](src/SkillSync.Daemon/Watchers/ProviderDiscoveryService.cs#L540), [SyncEngine.cs, 604–608, 765–780 and 891–981](src/SkillSync.Daemon/Core/Engine/SyncEngine.cs#L891).

**SYNC-02 · P0 · Supporting-file validation has a containment gap. Reproduced.** The common writer only checks the first component before combining paths. A model containing `scripts/../../audit-sentinel.txt` wrote a sentinel outside the fixture’s canonical skill directory. REST POST and PUT bind the full model and route it directly to that writer. MCP rejects `..` in one ingress, which leaves REST and other mutation paths exposed. The common validator also needs Windows device names, alternate streams, rooted paths, case collisions, reparse points, and path length checks. Validate the *complete plan* before any mutation. Resolve filesystem targets beneath configured roots, reject reparse-point traversal under the ownership policy, and use the same containment logic for reads, copies, and removals. A string prefix after `GetFullPath` alone cannot account for junctions. Evidence [SkillRestEndpoints.cs, 189–212 and 342–357](src/SkillSync.Daemon/Api/SkillRestEndpoints.cs#L189), [SyncEngine.cs, 1038–1098](src/SkillSync.Daemon/Core/Engine/SyncEngine.cs#L1038), [McpJsonRpcHandler.cs, 640–652](src/SkillSync.Daemon/Mcp/McpJsonRpcHandler.cs#L640).

**SYNC-03 · P1 · Resync overwrites changes made while SkillHub was closed. Reproduced.** Startup and manual resync discover new slugs only, then push every cached canonical document. Edit Gemini on disk without watchers and run full resync. The original canonical text replaces that edit. The primary target conflict code backed up the previous Markdown in the fixture. There is no merge or recovery UI, and secondary Codex/Antigravity writes bypass even that conflict check. First adoption or ledger loss skips backup when there is no recorded hash. Two near-simultaneous external edits can race: the queue stores paths, and the first event’s propagation can overwrite the second file before its queued event reads it. File-by-file comparison needs a base revision for each concrete destination, with a conflict result that retains both versions. Evidence [SyncEngine.cs, 390–498, 630–694, 787–859 and 983–990](src/SkillSync.Daemon/Core/Engine/SyncEngine.cs#L390), [MultiRootFileWatcher.cs, 35–39](src/SkillSync.Daemon/Watchers/MultiRootFileWatcher.cs#L35).

**SYNC-04 · P1 · A single consumer serializes writes while reads and merge decisions race outside it.** REST toggles, MCP patches, tag operations, startup resync, and UI saves clone snapshots before enqueue. Two disjoint edits can each succeed while the second loses the first. Status and list requests can see the cache ahead of durable writes. Discovery and catalog refresh can overlap with the consumer and each other. The unbounded queue has no backpressure, limits, or operation supersession. Canceling a caller’s `WaitAsync` can leave a queued write running. Disposal completes and immediately cancels the reader without resolving all queued completions. Inline event subscribers can throw during success or error publication. A subscriber exception from the catch block can terminate the queue and strand callers. Apply typed commands and revision checks inside the writer, bound and coalesce watcher work, and make shutdown resolve every admitted command as committed, canceled, or recoverable. Evidence [SyncEngine.cs, 24–55, 205–294, 296–367, 579–594, 744–763 and 1227–1257](src/SkillSync.Daemon/Core/Engine/SyncEngine.cs#L579), [SkillRestEndpoints.cs, 359–385](src/SkillSync.Daemon/Api/SkillRestEndpoints.cs#L359).

**SYNC-05 · P1 · Atomic file replacement is weaker than a durable skill operation.** The engine publishes the cache and expected hashes, then updates canonical, provider projections, and supporting files separately. A locked or failing destination can leave partial writes and skip later targets. The final ledger is a whole-file serialization under lock after each skill and some semantic no-ops. Ledger I/O failures are silent, a corrupt ledger becomes an empty ledger, temp ledger files can be stranded, version is unused, and hash/provenance state can diverge from the disk. Deletion persists the ledger change before attempting the file removals. The file writer stages same-directory temporary text files and retries some sharing failures, which is valuable. Its bounded retries, permissive concurrent reads, and final rename still leave races across operations and lack a crash-recovery protocol. Version the on-disk schema, separate intended and applied hashes, record recoverable operations and tombstones, and publish results after the durable commit point. ## 3. MCP, HTTP, and desktop shell

### 3.1 Public and local trust boundaries

**SEC-01 · P0 · Quick Tunnel can expose the entire privileged application.** Cloudflared forwards the same listener that serves static UI, REST, desktop commands, and MCP. ### 3.2 Protocol and lifecycle

**MCP-01 · P1 · The dispatcher advertises protocol support it never negotiates.** `initialize` echoes any version. A fixture offered `2099-01-01` and got it back. There is no lifecycle state or initialized/cancellation processing. Tool calls work before initialization. The handler ignores the `jsonrpc` field and does not validate the ID type. It conflates missing and explicit null IDs. A numeric `method` throws before the main error handler, reproduced. Through the pipe this can close a client connection. Batch input is rejected even though the source advertises the March 2025 HTTP contract, which supported batches. Newer revisions have different rules. Pin an explicit tested compatibility matrix and use protocol library transport handling where it fits. Validate JSON-RPC envelopes, tool arguments, sizes, and cancellation before dispatch. **MCP-02 · P1 · HTTP combines two incompatible SSE conventions.** GET `/mcp` and legacy `/sse` both emit the legacy endpoint event for `/message`. A client disconnect between lookup and write can close that channel after a mutation has completed. No explicit validation exists for a legacy target session before processing destructive requests. ### 3.3 Native shell and host

**DESK-01 · P1 · A machine-global singleton, fixed pipe, and guessed HTTP port undermine startup and profiles.** The global mutex and pipe name do not encode Windows user or configured home. Retain the native caption and tray affordance, centralize host shutdown, own all disposable UI resources, and persist validated bounds and System/Dark/Light settings. Test on mixed-DPI displays, runtime failure, logoff, tray restart, and repeated activation. ## 4. Installation, open-source readiness, and tests

**REL-01 · P0 · Repairing an existing Codex registration can destroy unrelated configuration. Reproduced.** Put `[mcp_servers.skillhub]` before an unrelated table in a disposable TOML file, then inject again. The unrelated table disappears. The regex enables single-line mode, so its greedy dot can consume later sections despite the inner lookahead. It also mishandles valid table spelling, comments, nested tables, and multiline strings. Presence detection uses a substring, even inside comments. An apostrophe in the executable path breaks the generated TOML literal. JSON repair preserves common object settings but rewrites the file, removes comments, replaces incompatible roots or `mcpServers` values, and replaces the entire SkillHub entry including user overrides. Injection may partially update a set of clients before one error aborts it. Uninstall swallows errors and can claim cleanup for any existing file. Replace the TOML regex and JSON rewrite policy with format-aware targeted editing, preserve unknown keys and raw text where feasible, validate before replacing, retain a recoverable backup, and verify the current fingerprint before commit. Evidence [InstallManager.cs, 184–258, 266–412 and 419–502](src/SkillSync.Daemon/Core/Engine/InstallManager.cs#L419).

**REL-02 · P1 · The standalone setup claim is unsupported by the implementation.** `build-installer.ps1` publishes a win-x64 self-contained single-file host with native extraction and copies that host as `SkillHub-Setup.exe`. The project marks the frontend as publish content. An isolated publish using the script’s flags succeeded and emitted a roughly 190 MB executable alongside a separate `wwwroot` directory. Copying the executable alone excludes those assets. The publish also reported three IL3000 warnings where single-file builds contain `Assembly.Location` fallback code. More fundamentally, the `--install` handler resolves the current executable or override, writes an icon beside it, and registers that location. It never copies an installed payload to the documented `%LOCALAPPDATA%\SkillHub` destination. Renaming or removing the downloaded setup executable can break shortcuts, auto-start, and MCP config. The developer script publishes framework-dependent into the install location and runs different steps, with no staged upgrade or prerequisite check. Choose a real installer that installs the full payload or explicitly distribute a portable bundle. Add an installation manifest, install/upgrade/rollback smoke tests, WebView2 prerequisite handling, release signing and checksums. Evidence [build-installer.ps1](build-installer.ps1), [install.ps1](install.ps1), [SkillSync.Daemon.csproj, 3–26](src/SkillSync.Daemon/SkillSync.Daemon.csproj#L3), [Program.cs, 112–193](src/SkillSync.Daemon/Program.cs#L112), [README.md](README.md).

**REL-03 · P1 · Install, repair, and uninstall modify a wide scope with unreliable completion reporting.** Install kills processes by common names, seeds an auto-activating bootstrap, writes and syncs provider skills, and registers every detected client and login launch. The PowerShell script force-stops by name and deletes deployed web assets before verifying the new publish. It does not explicitly check native publish/installer exit status. Shortcut creation deletes old links and suppresses errors. CLI `--home` does not isolate real AppData, registry, shortcuts, or other running processes. Repair again registers auto-start. Uninstall removes configured names without recording who created them, retains provider projections and bootstrap instructions that can point to a removed MCP server, and leaves binaries behind. A process handle is treated as successful launch without a readiness handshake. Use separate install, connect-client, auto-start, and adopt-existing-skills steps with accurate per-step results. Uninstall should remove only owned integrations and offer a clear cleanup of projections after backup. Evidence [install.ps1](install.ps1), [Program.cs, 112–220](src/SkillSync.Daemon/Program.cs#L112), [InstallManager.cs, 50–59, 537–651 and 668–750](src/SkillSync.Daemon/Core/Engine/InstallManager.cs#L668).

**REL-04 · P1 · Platform-neutral source is not yet a cross-platform release.** The only app and test targets are Windows with WinForms. The entry point always runs Windows Forms on the daemon path. The shell script publishes the Windows project and expects an executable called `SkillHub` without the Windows suffix. LaunchAgent and systemd code generate files but ignore exit status from their service commands and leave stdout/stderr undrained. The existing test checks strings, not registration. Split the portable engine and headless host into `net8.0` projects, keep the WinForms shell and Windows installer Windows-targeted, and remove or label unsupported release scripts until a platform passes install, lifecycle, and transport tests. Evidence [SkillSync.Daemon.csproj, 3–15](src/SkillSync.Daemon/SkillSync.Daemon.csproj#L3), [install.sh](install.sh), [Program.cs, 345–365](src/SkillSync.Daemon/Program.cs#L345), [InstallManager.cs, 853–981](src/SkillSync.Daemon/Core/Engine/InstallManager.cs#L853).

## 5. Implementation roadmap

### Phase 0 · Stop destructive behavior and close the network boundary

**Order** · Add isolated regression fixtures first. Land a small safety release before the larger architecture work.

1. Disable Quick Tunnel and its boot flag in the current distribution. Authenticate privileged loopback routes and restrict accepted origins. Restrict named pipe connections to the intended local user. Remove tokens and raw paths from unrestricted status and logs. Probe the public and local route matrices from a second user/browser origin. Public clients must have zero access to desktop REST, static UI, settings, and configuration repair.
2. Centralize root validation in the shared filesystem boundary. Resolve and validate every planned path, including deletes and reads, before applying a command. Reject traversal, ambiguous Windows paths, reserved names, unsupported symlink/junction boundaries, and collisions. Test the same invalid bundle through REST, MCP, file import, catalog promotion, and raw engine calls. The fixture sentinel outside the skill root must remain untouched.
3. Introduce operation types for library delete, target disable, observed provider removal, and companion-file removal. Tag or correlate SkillHub’s own filesystem changes by concrete path and operation, including deletes. If a provider copy disappears, record the target as missing and allow repair or deliberate disable. An explicit library delete should stage an undoable tombstone and operate only on owned copies. Fixtures must prove that disabling Gemini keeps the canonical and other provider copies, removing a companion affects exactly that companion, and restarting cannot resurrect an intentionally removed skill from a residual projection.
4. Stop destructive automatic config repair. Replace the TOML path with a validated parse and minimally scoped edit. Preserve later tables, nested tables, quoted names, comments, custom env/timeout settings, and any unowned legacy name. Stage and validate the result, preserve an exact-byte backup, and report each client separately. Regression gates should include the reproduced unrelated table failure, malformed files, concurrent edit detection, apostrophes and spaces in paths, and reversible uninstall.
5. Make canonical writes explicit about create, replace, clone, and patch. Detect slug collisions and return a conflict with the destination and existing revision. Block system mutations centrally. Make full resync preview changed/deleted/foreign files before overwriting. Keep current backend/client contracts compatible where they can be retained safely.

**Exit gate** · All P0 repros are in automated tests and pass. Existing user files remain byte-identical outside the operation plan. Every failure preserves the last usable canonical version and reports the affected target or config file.

### Phase 1 · Make the filesystem a reliable source of truth

Keep `~/.skillhub/skills/<slug>/SKILL.md` and its bundle as the human-editable source. Keep the ledger and recovery records as versioned files. The store needs three concepts with independent lifetimes.

| Concept | Suggested representation |
| --- | --- |
| Managed skill | Stable identity, human title, current slug, revision, Markdown, owned bundle manifest, optional origin link, target intent. The slug identifies the external filename. Existing slugs can remain the initial identifier during migration. |
| Catalog entry | Source family, source identifier, source-relative path, version or commit, summary metadata and trust/license hints. References to managed copies resolve through the origin link. |
| Destination | Concrete provider client, root, format, and relative path. Applied revision and hash, prior observed hash, ownership, and latest result. Gemini and Antigravity, Codex and Agents, can have distinct health while grouped in the UI. |

1. Add a platform-neutral command layer for create, edit, clone, import, activation, disable, reconcile, and delete. REST, MCP, and watcher observations go through that layer. Resolve merges and stale revisions inside the single writer. Give each command an ID and result. Use idempotency for retries after transport timeouts.
2. On startup or watcher invalidation, compare the last applied base, current canonical bundle, and observed destination bundle before writing. If only one side changed, apply a presence-aware provider merge. If both changed, surface a conflict and preserve all versions. If ownership is unknown, surface an adoption decision. Run these rules on observed deletion and watcher overflow. Avoid treating a transient sharing violation as deletion.
3. Separate canonical commit from projection attempts. Stage the canonical document and manifest, write a recovery record before replace, record the committed revision, then project that revision independently to each destination. Record per-target success or retryable failure. Journal enough information to resume or roll back after crashes between operations. Version ledger migration and verify a backup before upgrading. Rebuild from canonical plus ownership/recovery evidence if the ledger is unreadable. A missing ledger cannot authorize destructive takeover.
4. Move format normalization and path handling into a provider registry with small adapters. A descriptor defines root discovery, read/write capabilities, format versions, supported field edits, and projection paths. Use an explicit extension metadata contract and a single validation policy. Add a fixture repository per supported provider version for round trips, clearing, unknown properties, Unicode, bundle paths, and generated output.
5. Replace synchronous full-catalog loading with a metadata index and lazy bundle reads. Snapshot catalog updates atomically and evict removed entries. Fetch only summaries for list, counts, and tags. Keep search indexed over opted-in body fields or load them asynchronously. Use paged results and a bounded cache. Pure catalog browsing should leave managed storage and the ledger untouched.
6. Publish small revisioned activity events. Status should report `Detected`, `MCP registered`, `Watching`, and per-target deployment results from separate data. Make reconciliation/repair return a job summary with progressed, skipped, conflicted, and failed counts.

**Exit gate** · Restart, process kill between writes, provider change while offline, two concurrent clients, deleted or unavailable roots, duplicate slugs, and 500–5,000 catalog entries are exercised with isolated fixtures. Two different providers editing the same base produce a recoverable conflict. A second resync on an unchanged tree makes no material writes. Catalog-only entries produce zero ledger entries.

### Phase 2 · Redesign Library, Reader, and Editor around user tasks

**Navigation.** Give the shell one persistent navigation row and one contextual action area. Keep the brand small. On wide screens, use a short navigation rail or one category row, with Library, Explore, and Settings as stable destinations. At narrow widths use one compact location control and an overflow menu. Move theme and installation controls into Settings. Keep a quiet connection indicator with accessible text and show an issue count only when action is needed. Remove the interactive overview strip. Put the current result count beside the view title or search.

**Library.** Default to My Skills. Keep Built-in & Templates and System explicitly discoverable, and show Plugin Catalog as a distinct source within Explore with a direct entry from Library. Active & Synced is an overlapping view of managed skills with verified current deployment to at least one provider. A skill can have one current target and one failed target, both visible. Show pending or failed operations via filters and provider details, including those with zero current copies. Preserve the managed template’s presence in Templates and reflect it in Active when it has a current projection. A customized copy enters My Skills only after a unique clone operation. Provider-owned System entries are read-only, with status and paths available in diagnostics.

**Search and tags.** A single query pipeline accepts collection, term, origin, tags, provider, and deployment status. Display removable filter chips and Clear All outside any disclosure. Current Tab stays within the named collection. All Skills switches to a visible cross-library results context, including explicit System scope if the user requests it. A category action selects a collection predictably and preserves only compatible filters. Counts use the same result scope. Tags get a durable canonical representation. If standalone unassigned tags remain part of the product, store them in a versioned local tags file and share that data with MCP. Limit inline tags to a small number plus a count, and give management its own panel with affected count and undo for bulk operations.

**Results layout.** Use a compact keyboard-operable result list as the primary layout for a large catalog. Each row has one focusable title, one useful description or matched excerpt, one provenance label, and concise deployment status. Group or truncate secondary metadata with a visible count and inspect it in the Reader. Preserve list focus and scroll across detail navigation and refreshes. Offer a wider detail split where it improves scanning. At docked sizes, replace the results view with a full-width detail screen and a reliable Back action. Keep filters within a height-bounded drawer or dialog so a populated tag set cannot displace results.

**Reader.** Make the document the main object. Place title, origin, and short summary above it. Keep one primary action based on ownership, with a labelled overflow menu for export, output preview, and destructive actions. Expose deployment under a clear “Sync destinations” control with state, revision, and per-target repair. Allow tag edits on managed items and deliberate user annotations on catalog entries if that feature is supported. Keep content scroll stable across metadata updates. Use safe structured Markdown rendering. Ship a tested renderer as a local asset or implement a bounded, explicitly documented subset with fixtures. Preserve the dependency-free runtime and avoid remote scripts. Provide an explicit bundle export and a separate Markdown-only export.

**Editor.** Put instructions near the top, below title and compact purpose/trigger fields. Keep save and cancel accessible in a stable action row. Use a real draft with revision and dirty state. Guard navigation, keep the draft after a failed save, and surface field errors in place. Show Draft/Saving/Saved/Sync issue states with a persistent result. Use sections for Instructions, Deployment, and Files, with real provider context and the ability to inspect destination-specific output. File paths and duplicates validate before submission. Output preview can run on demand or use an abortable, generation-checked request. The preview must identify the exact draft and effective destination, and show any lossy transformation or unsupported metadata.

**Interaction foundation.** Keep vanilla modules. Introduce a single navigation action and render from an explicit screen/draft state. Split the existing mega-components into Library, Reader, Editor, Explore, Connections, and Activity modules with shared accessible controls. Use isolated request state per view and per operation. Keep focus, loading, retries, errors, and selected identities in those view states. Update visible data from small events and authoritative snapshots.

**Exit gate** · At 460 × 500 and at the native form’s actual minimum client area, results and all drawer actions are reachable by mouse and keyboard. Validate 1280 × 820, a full-HD monitor, 125% and 150% DPI, and keyboard zoom/reflow. Verify Ctrl+K from every screen, focus restore, no stale provider state, durable draft protection, a unique clone, and identical library and MCP counts under the same filter. Meet WCAG 2.2 AA for the covered desktop web content, including measured contrast, focus visibility, and keyboard traversal. [W3C WCAG 2.2](https://www.w3.org/TR/WCAG22/).

### Phase 3 · Make discovery and setup trustworthy

1. Give Explore a permanent route. At wide sizes use list/preview. At narrow or short sizes use results → detail and Back. Keep the primary toolbar compact. Show source and topic scope next to the actual search. Display meaningful loading, offline, rate-limited, empty, unavailable, and already-imported states. Never leave a stale preview actionable after a selection change.
2. Give direct URL, file, and catalog import the same staged review. Resolve an immutable revision and exact manifest, show provenance, license status, file previews, conflicts, and chosen targets. Apply an import plan by ID with matching revision. Handle duplicate titles and destination slugs, preview failure, and batch partial outcomes explicitly. A newly imported item can land in My Skills as a draft with activation chosen deliberately.
3. Structure Settings around **Connections**, **Appearance & startup**, and **Diagnostics**. Connections show each installed client, effective paths, registered command health, restart requirement, and per-client connect/repair/remove. Appearance shows System/Dark/Light, startup, and close-to-tray settings. Diagnostics show watcher health, operation history, backup restore, and rescan/reconcile results. Remote access stays disabled until its dedicated trust boundary ships.
4. Pin supported MCP revisions and test them with real clients or protocol fixtures. Keep stdio proxy launch quick and deterministic, remove the competing-writer fallback, and expose a versioned, user-scoped daemon handshake. Replace hand-built transports where a supported MCP library supplies the needed lifecycle and authorization. Keep internal pipe messaging private. Verify EventSource payloads against an actual browser, including reconnection and a dropped event.
5. Harden WebView2 navigation, downloads, permissions, messages, and recovery. Keep window chrome native. Save position and theme, support keyboard and accessibility settings, and make the tray show user-visible failure or offline status. Prove that closing to tray and signing out behave consistently.

**Exit gate** · A first-time user can inspect discovered clients, connect one, create a skill, verify its destination, import a pinned bundle, and recover a conflict. Validate with the initial import racing another selection, zero results, preview fetch failure, missing runtime, client restart, and canceled repair.

### Phase 4 · Ship a credible open-source Windows release

1. Make the project names and version source coherent. Keep legacy root/name aliases in a versioned migration with compatibility tests. Move the portable domain and adapter code into a platform-neutral project with independent tests. Separate local daemon, desktop shell, and install integration along the existing product boundaries.
2. Decide supported Windows versions, architectures, .NET runtime distribution, WebView2 prerequisite, and first supported client versions. Build a signed, reproducible package with a stable installed path and all web assets. Test launch from Start Menu, app restart, upgrade, rollback, and removal under a standard user on a clean VM. Validate login behavior, custom port handling, missing WebView2, conflicting process, and uninstall ownership. Document any separately distributed portable build.
3. Publish a license, dependency and asset attribution, a provider-contributor guide with a working adapter fixture, release checksums, and a security contact. Document what stays local, what touches the network during browsing, what install writes, and how users recover a provider edit. Align README, CLI help, release artifacts, and screenshots.
4. Run Windows CI with engine, watcher, config, packaged app, and browser coverage. Add platform-neutral jobs once the engine can build independently. Benchmark 500 and 5,000 catalog rows with representative body and bundle sizes. Record machine, cold/warm time, list payload bytes, peak heap, rendered rows, and request count per activity burst. Suggested initial acceptance targets are first useful cached library paint within 1 second on a defined reference machine, p95 keyboard filter feedback under 100 ms, and bounded DOM/cache growth with paged results. Treat these as proposed targets to baseline and tune.
5. Gate public release on completed P0 and P1 safety and core-flow checks. Use a limited preview to validate provider compatibility and installer recovery before presenting automatic sync as stable.

### Phase 5 · Add profiles after ownership and conflict handling are stable

Store each profile as a local, versioned selection of managed skill IDs and target preferences. Keep content identity independent of profile membership. A profile switch generates a reviewable destination diff, applies only owned projections, and records its operation for undo. Reconcile edits against the active profile’s revision. Separate user and workspace roots and test two profiles selecting different variants with the same provider path. Expose the active profile in navigation and status and document exactly what happens to each destination when switching. Keep profile defaults out of the sync engine until the destination ownership contract can enforce them.

## 6. Highest-value regression scenarios

| Scenario | Required observable outcome |
| --- | --- |
| Disable a provider while live watchers are active | Only that owned projection is withdrawn. Canonical skill, other providers, and intent history survive. |
| Delete, modify, rename, or move one companion | Correct bundle change, no unintended skill removal, deterministic handling of unsupported files. |
| Run repair with an existing TOML entry, later tables, and user overrides | A targeted semantic diff. Unrelated content survives and backup restores exact bytes. |
| Edit canonical and a provider independently before starting | Both revisions retained. Conflict appears in Reader and Activity with a resolution path. |
| Crash after canonical commit or during target deployment | Restart recovers or retries pending steps. UI states distinguish saved and applied. |
| Present a crafted path or use a different local identity/origin | Rejected before I/O. The document, ledger, and paths outside the authorized root remain intact. |
| Open a private/public HTTP or pipe path with an invalid credential | No response data or mutation beyond the documented authorization error. |
| Choose two Explore results out of order, then filter to zero | Visible detail follows selection. Import stays disabled when the selection is invalid or pending. |
| Toggle a provider from the Reader and refresh another client | Correct badge, button state, counts, and document revision across interfaces. |
| Search, browse, edit, and import at minimum size in both themes | Content and controls remain visible or reachable, focus stays predictable, no keyboard trap. |
| Install, upgrade, restart, and uninstall a signed package on a clean machine | Complete UI assets, stable app path, verified client registrations, and recoverable user data. |
