# SkillHub UI/UX audit and redesign blueprint

13 November 2026 · Installed SkillHub 1.1.1 · Web assets 20261113-v10 · Source 01346a7

## Executive findings

1. **The four personal skills have an ownership conflict with identical content.** Each Antigravity bundle matches its Gemini counterpart byte-for-byte. SkillHub's previous sync code wrote Antigravity mirrors without recording their ownership separately. The current engine protects unknown files by creating backups, and the interface presents that safeguard as a content problem. The appropriate resolution for these four records is a verified, ledger-only recognition of an existing mirror, with a separate flow for genuinely differing content.
2. **Changing Theme in Settings has two distinct effects.** Selecting Dark gives no preview. Clicking Save preferences applies Dark to both the web surface and the native Windows title bar, then silently disables sign-in startup and close-to-tray. The UI sends snake_case keys for those two values, while the request type binds camelCase. The live test reproduced both effects. The saved Light theme and both enabled startup options were restored and verified on disk and in the registry.
3. **The app presents diagnostic data where people need a decision.** Library warnings open a long document, the underlying conflict sits beneath the body, and Diagnostics offers only an inactive duplicate. The next step should be available where the warning appears.
4. **The design has too many equal-weight surfaces.** The header, category counts, filter controls, provider badges, cards and repeated origin labels compete for attention. Healthy rows need less furniture. Exceptional rows need specific language and an action.
5. **Read, edit and import lose continuity.** Reader tools sit beneath long content, file editing and output preview behave like separate modes, and Explore hides the import controls beneath the full document. The redesign should keep the user's place and bring the next decision into view.

### Evidence and coverage

- **Live** means observed in the installed WebView2 window on the real profile. This covered the Light Library, four personal rows and category counts, provider and theme header labels, Settings Connections, the Appearance & Startup screen, the theme selector, and Light-to-Dark save including native title bar and startup effects. The capture was approximately 1011 × 666 window pixels. The desktop session received an Escape stop during the audit. No further Windows UI automation was used.
- **Disk** means read-only inspection of the live skill directories, both ledgers, and the conflict snapshots. All 16 installed web assets matched the checkout by SHA-256.
- **Fixture** means Chromium using the actual frontend with controlled API responses in a disposable browser profile. The existing interaction harness was run in memory at 1280 × 820 and 480 × 600, with the existing light and dark token-contrast checks at both widths. It passed. The exercised flows included Library category navigation and multi-tag logic, provider overview, theme shortcut, Reader and tag dialog, Editor discard guard, Explore list and preview race, failed preview, successful staged import, Settings save, and event refresh. Fixtures do not cover native chrome, live discovery, actual Windows registry binding, or all screen/theme combinations.
- **Source** means traced through the frontend or its backing routes and services. The inventory below distinguishes source findings from tested interactions. The full matrix of every screen and modal in both sizes and themes could not be completed on the live profile after the stop. Destructive or profile-changing actions beyond the reversible theme test were not applied to the real data. The audit is the only project deliverable.

## 1. Why the four personal skills have conflict backups

### What is on disk

Every path in this table ends with `<skill>/SKILL.md`. Hashes are abbreviated SHA-256 of raw bytes. Supporting files were also compared by relative path and raw hash.

| Personal skill | Canonical | Gemini and Antigravity | Codex and Agents | Matching Gemini/Antigravity companion files |
| --- | --- | --- | --- | ---: |
| Capture Reusable Lessons | `b8041f74f13bd199` | `51fc7b2cf65e5855` | `361ff85ef875e218` | 0 |
| Chat Handoff | `66fd6603824826d7` | `b92a8e2b35504874` | `cfe8bd2140196a6c` | 0 |
| Roblox Development | `b5fd301c89ba86ce` | `67f3c22a6367b786` | `2a0abfe6d0492636` | 5 |
| Web Project Runtime | `01e64b3e0f298022` | `506e126c34194a6e` | `a8c1c33410cc95d0` | 1 |

- Canonical is under `~/.skillhub/skills/`, Gemini under `~/.gemini/skills/`, Antigravity under `~/.gemini/antigravity/skills/`, and the Codex copies under `~/.codex/skills/` and `~/.agents/skills/`.
- Each pair of Gemini and Antigravity documents has the same raw bytes and the same file creation and last-write time, **11 November 2026 at 19:02:18 UTC**, at second precision. All four pairs use LF. Their frontmatter and companion manifests match exactly. The instruction bodies also match the canonical and Codex bodies when compared after frontmatter and outer whitespace are removed. Different frontmatter across those formats is expected. Three `~/.codex` bundles additionally contain `agents/openai.yaml`, which is absent in the corresponding `~/.agents` bundle. Those files are outside the failing Antigravity destination and require separate ownership evidence before any cleanup.
- In `~/.skillhub/.sync-ledger.json` schema v2, each personal skill is at revision 1. The Gemini primary, Codex primary, and Agents mirror each report `synced`, `owned: true`, applied revision 1. Each Antigravity mirror reports `conflict`, `owned: false`, applied revision 0, with “The destination already contains an unowned skill.” The older `~/.skillsync/.sync-ledger.json` still exists and contains only the legacy bootstrap entry. The predecessor of the current `~/.skillhub` ledger was not available as a separate file.
- Each personal skill has one conflict JSON written **13 November at 09:37:39 UTC** (10:37:39 Brussels time). The backed-up Markdown exactly matches the current Antigravity file and the backed-up companion files match as well. The JSON contains destination, Markdown and supporting files. The reason lives in the ledger/activity, while the filename encodes time. There is a fifth backup for the system bootstrap. Its Gemini and Antigravity Markdown differ, so it must be evaluated independently.

### What caused the warning

The most likely provenance is SkillHub's own legacy Gemini-to-Antigravity projection. At `208a1be`, the write path pre-registered the main provider path and gave the Agents mirror a separate `codex_agents` record. The Antigravity branch wrote the **same** Gemini-rendered Markdown and supporting files without adding a per-mirror ledger record. The matched creation and write times, equal bundles, upgrade-time backups and current ledger state all support that explanation. The exact historical writer cannot be proved from an absent prior ledger record or timestamps alone.

During upgrade, `MigrateLedger` carries forward existing v1 destinations. `MigrateTargetAsync` can establish primary ownership where the recorded old raw hash matches. Reconciliation discovers the Antigravity path, adds a fresh target with no ownership, and reaches the unowned-file branch in `ProjectAsync`. That branch saves a conflict before comparing the observed bundle with the intended bytes as evidence of a safe equivalent mirror. A matching conflict hash subsequently short-circuits reconciliation, so a rescan repeats the state. For these four files, the trigger was missing ownership history. A content, frontmatter, line-ending or companion difference is ruled out between Gemini and Antigravity. [Legacy sync write path](https://github.com/KamilTahiri/SkillHub/blob/208a1be0aa7a99a9dabfef6411059725432a26d1/src/SkillSync.Daemon/Core/Engine/SyncEngine.cs#L851), [current ledger migration](src/SkillSync.Daemon/Core/Engine/SyncEngine.Storage.cs#L10), [current projection branch](src/SkillSync.Daemon/Core/Engine/SyncEngine.Reconciliation.cs#L391).

### Why the current interface cannot resolve it

- Library announces “Synced to Gemini” and “Needs attention: Gemini” together. These describe two destinations, but the same badge vocabulary makes them sound contradictory. The visible warning never says Antigravity or identifies its cause.
- Clicking the row opens the skill. The Reader repeats “Needs attention” with no review link. The actual destination paths, repeated status lines and long backup path sit in a collapsed section after the full Markdown. This can require scrolling through thousands of words just to reach the cause.
- Diagnostics lists the slug and absolute path, then offers **Recover as copy**. The response creates an inactive personal skill under a random suffix. The existing target, warning and backup remain. The same backup can be recovered more than once. There is no compare action, open-source-skill link, resolved marker, historical grouping, date, provider label, change summary, or explanation of whether the original is safe.
- The backend diagnostics summary returns at most 100 readable snapshots. It sorts on full paths, so the selected 100 can favor slug order instead of newest date. Unreadable or incomplete snapshots disappear without an indicator. Raw activity repeats the backup location in a second place. [Diagnostics API and recovery](src/SkillSync.Daemon/Core/Engine/SyncEngine.Diagnostics.cs#L8), [Settings Diagnostics](src/SkillSync.Daemon/wwwroot/js/components/statusBar.js#L86).

### Resolution design

Put **Review Antigravity** beside the Reader warning and make it reachable directly from the Library exception cell. In Diagnostics, show one row per skill and destination with title, exact target, reason, timestamp and current status. Move full paths and retained copies under Details. Expose **Open skill** and **Review**.

| Reason | Default review | Proposed resolution |
| --- | --- | --- |
| Matching legacy mirror | “Antigravity already has an identical copy. SkillHub has no ownership record for it.” Show “0 changed files” with provenance evidence. | **Recognize existing mirror** updates the ledger after checking the current canonical revision and all live destination hashes. Keep the historical backup and mark the issue resolved. |
| Unverified external file with identical content | “An identical copy is present. Its ownership is unverified.” | **Leave provider-managed** records an acknowledged, usable external copy tied to the observed fingerprint. A later file change reopens review. Offer explicit adoption separately when ownership and future cleanup consequences are understood. |
| Different provider content | Separate body, normalized frontmatter, supported files added/changed/removed, and untouched external files. | **Keep SkillHub version**, **Accept provider version**, or **Keep separate copy**. Each choice previews affected destinations and retains a snapshot. Preserve canonical metadata when accepting a provider format with fewer fields. |
| Missing or failed destination | Name the path and failure reason, such as write blocked or file removed. | **Retry deployment** or **Restore missing copy** for that destination. Surface partial success and retain the canonical revision. |

Require a compare result based on the current intended projection and the current destination, including complete supported-file manifests. Comparing Gemini with Antigravity is strong provenance evidence and should not by itself grant ownership. Never infer ownership of arbitrary companion files from a matching primary. A one-click resolution should mean one explicit decision after the comparison is visible. Batch recognition may cover the four verified equivalents, with per-destination outcomes. Keep the bootstrap out of that batch.

## 2. Theme behavior and the Settings data-loss bug

### Live reproduction

1. Open **Settings → Appearance & Startup** on the installed app. The theme was Light, with both **Start SkillHub when I sign in** and **Keep SkillHub running in the tray when the window closes** checked.
2. Select Dark. The selector says Dark. The web surface, header icon and native title bar remain Light. There is no pending-change cue. The Save preferences button is visually grouped under Startup and window behavior.
3. Click **Save preferences**. The window and native title bar turn Dark and Settings reports “Preferences saved.” Both startup checkboxes turn off. On disk `Theme` became `dark`, `CloseToTray` became `false`, and the current SkillHub Run registration was absent.
4. Restored the saved Light theme, close-to-tray and sign-in startup using the installed executable's documented registration shape. Verified the file and registry values. The running settings store caches its file, so a fresh process is required to prove the native session has reloaded that restoration. No restart was used to continue the interrupted UI inspection.

### Event, HTTP and native path

- `index.html` boots with `data-theme="dark"` and a disabled quick-theme button. `main.js` applies the OS preference, then reads persisted preferences. `state.js` contains request-generation, provider and filter helpers. It has no theme store or event binding.
- In `statusBar.js`, `renderPreferences` creates a select without a change handler. Only the Save callback reads its value and calls `api.preferences`. Navigation away silently loses an unsaved choice. The independent header button applies optimistically and PATCHes only Theme. An already-open Settings select does not update when the header changes the saved theme. The stale field can then overwrite the header choice on Save.
- The Save payload is `{ theme, close_to_tray, auto_start }`. The default ASP.NET input binder expects `theme`, `closeToTray` and `autoStart` for the positional `DesktopPreferenceRequest`. The underscore keys are unbound and both bool values default to false. The route unregisters startup as needed and stores false for close-to-tray. It returns a snake_case response that correctly updates the visible checkboxes to their newly disabled values. The fake browser endpoint accepts the supplied JSON directly and misses the production binder failure.
- After successful PUT, `main.js:applyTheme` updates the root dataset, button icon and label, then posts the effective theme over WebView2. `SkillHubDesktopShell.cs` verifies origin, reads that message, and updates the WebView background, DWM caption and border. Live Dark save reached both surfaces. System appearance on initialization can still flash because the markup, native initial color and asynchronous persisted setting are resolved separately. Native host message/application failures have no acknowledgment to the frontend.
- Styling compounds the feedback issue. While Save is disabled the button fades, and the hover rules can temporarily combine accent-text with a raised background. The live Dark capture showed very faint Save text immediately after submission. Test the composited disabled/focused/hovered states separately from static palette pairs. [Settings event](src/SkillSync.Daemon/wwwroot/js/components/statusBar.js#L68), [API client](src/SkillSync.Daemon/wwwroot/js/api.js#L46), [PUT route](src/SkillSync.Daemon/Api/SkillRestEndpoints.cs#L61), [preference request](src/SkillSync.Daemon/Desktop/DesktopPreferences.cs#L8), [theme application](src/SkillSync.Daemon/wwwroot/js/main.js#L218), [WebView message](src/SkillSync.Daemon/Desktop/SkillHubDesktopShell.cs#L396).

### Design and acceptance

Use **System / Light / Dark** as a single-selection control with immediate app and caption preview. Persist only the selected theme through the existing theme-only route and reflect one shared value in Settings and the header. Keep startup and tray as independent preferences with their own feedback. Use explicit JSON keys for mutable requests, and reject missing required settings instead of defaulting to false. Any startup registration error should stay beside its own control and leave appearance usable. Confirm with real loopback HTTP and WebView2 tests that a theme change preserves enabled and disabled combinations, quick-toggle and Settings stay consistent, OS-follow updates correctly, the caption follows the web surface, and restart restores the preference without a theme flash.

## 4. Screen-by-screen critique and blueprint

### Library, search and tag management

**Live.** The first view shows “My Skills” in the title and tab, then “4 skills” and a second “4” in the tab. All four rows repeat “My Skill,” Codex, Gemini and the same amber message. “Active & Synced 4” also contains those four, though they each have an unsynced Antigravity mirror. The provider names are useful on heterogeneous rows. Here the repeated boxes dominate the title and description while the amber phrase gives no diagnosis. The sticky shell can cover the top heading when returning at a previous scroll position.

**Fixture and source.** Tabs are real buttons again. The live counts reflect the currently filtered dataset, yet the interface gives no clue that “My Skills” and “Active & Synced” overlap. The displayed count can still come from the old query during “Searching…” because tabs are derived from previous matches until the response lands. A failed search can likewise leave convincing old counts. The UI fetches all skills despite the REST API supporting paging, then renders in batches of 50. There is no sort control, saved view, or query persistence after a restart. When every initial snapshot request is not ready, Promise.all can cause a provider or tag failure to hide otherwise available skills.

**Filters.** The split between main query, tag query, Match all/any, tag pills, four facets, applied chips and a clear action is functionally powerful and visually crowded. The selected tag appears in both the drawer and the applied-chip strip. “Clear filters” also clears the search text. “All skills” excludes System, silently leaves the current collection on tab selection, and lacks a visible top-level scope choice. Provider filtering matches confirmed sync or issue only. A skill targeting an enabled provider but still pending cannot be found through that facet. “No matching skills” leads to Browse Plugin Catalog instead of restoring the local result set. On a narrow viewport the scrollable tags sit inside another scrollable filter section, below two rows of tabs. Keyboard and wheel users can lose their expected scroll target.

**Tag manager.** Reached through Tags & filters → Manage tags. The modal includes create, per-tag rename and delete, and Undo after a mutation. It gives almost no guidance when the registry is empty. There is no search within the manager, usage link, bulk tagging or merging preview. Rename and delete create nested dialogs. The impact count represents managed usage, while the filter bar also derives tags from catalog or system rows. That makes the taxonomy appear editable in places where it is read-only. The engine holds only one undo record and a later edit can invalidate it. The UI offers Undo without explaining that lifetime.

**Design.** Keep one search and collection header with a single result count. Use a compact list with columns **Skill / Providers / Issue** at 1280 px, and stack the last two as one secondary line at 480 px. Show origin only when it adds provenance. Treat healthy provider glyphs as quiet indicators. Put real exceptions in a short “Antigravity copy needs review” affordance, separate from opening the skill. Use a lightweight filter popover or single scroll drawer with a searchable tag list, a clear AND/OR control and active chips shown in one place. Put scope in the main control, define whether it includes System and plugins, and keep **Clear query** distinct from **Clear filters**. Move tag administration to a focused Library task with usage links and explicit merge/delete impact. Preserve the last item, filters and scroll when returning from a detail view. [Library render and filters](src/SkillSync.Daemon/wwwroot/js/components/skillList.js#L149), [filter state](src/SkillSync.Daemon/wwwroot/js/state.js#L65), [snapshot loading](src/SkillSync.Daemon/wwwroot/js/main.js#L138).

### Skill Reader

**Hierarchy.** The source assembles Back, title, origin/status, tags, description, When to use, the entire document, destinations, files and source details in a single vertical stack. The document has a 77ch measure inside a wider page, so the long full-width header and hidden diagnostic section bookend a narrower text column. On a long skill, provider controls and supporting files sit several screens below the warning. The generic Actions button is almost as prominent as Edit and opens a full modal for a short command list. The same description or instruction heading can appear above and within the Markdown. When the first Markdown heading fails the title comparison, the renderer can add a second H1.

**Controls and failures.** Provider disable correctly prompts about withdrawing owned copies, but applies to the logical provider group. Gemini and Antigravity share one switch even when only one has a problem. Repair is offered only when some target is missing. A conflict or write error has no contextual resolve/retry path. Disabled and undetected destinations still occupy disclosure rows. Tag deletion is immediate with a small ×, without undo in the Reader. The Add tag modal uses a datalist and lacks a consistent Enter submit path. New snapshots rebuild the article and can reset selection, focus or open state if keys change. Native HTTPS links look navigable but clicking copies the URL. The shell cancels external navigation and denies permission requests, so Clipboard success should be verified in WebView2 and given an explicit selectable fallback. Relative links outside the supported path pattern can become inert text. Export uses a download without durable success or failure feedback once handed to the native host.

**Design.** Use a stable detail header with breadcrumb, compact type/origin, Edit and a contextual menu. Place an issue banner and Review action directly beneath the title. Add a sticky section strip for **Instructions / Files / Destinations** with counts only when useful. On desktop, use a narrow right inspector for tags, source and deployment details. At 480 px use a single reading surface with the inspector available as a sheet or section switcher. Keep destructive commands in their existing confirmation path. Provide copy/export outcomes and explicitly label a copy-only link. Improve Markdown semantics for headings, nested lists, table alignment, task lists and local references before claiming full Markdown fidelity. [Reader layout and actions](src/SkillSync.Daemon/wwwroot/js/components/skillReader.js#L42), [destination controls](src/SkillSync.Daemon/wwwroot/js/components/skillReader.js#L124), [Markdown links](src/SkillSync.Daemon/wwwroot/js/markdown.js#L17), [WebView navigation and permissions](src/SkillSync.Daemon/Desktop/SkillHubDesktopShell.cs#L356).

### Skill Editor, files and output preview

**Hierarchy.** The sticky Save / Provider output / Cancel row appears before the Title field. Preview Markdown appears later below the instruction textarea. The two preview concepts are unrelated in placement and the latter has no preview mode that keeps the source visible. Description and When to use compete for attention while a plain textarea carries the primary work. Tags use comma entry here, a datalist in Reader and chips in the Library. Each supporting file expands to its own panel with path and a large textarea, so a bundle with several files becomes a lengthy vertical form. Provider enablement, Codex summary, Claude tools and Cursor globs sit in one disclosure.

**Control risks.** A new skill starts with all provider preferences enabled, including undetected providers. The call to action says “Save skill,” which hides the distinction between local creation and projection. A clone defaults off. The eventual deployment consequences depend on provider state and are insufficiently visible. Slug validation and duplicate path errors appear in general feedback, which may be above the viewport, without field-level messages or a name collision route. Removing a supporting file changes the draft immediately; only the whole-draft discard guard protects it. Draft recovery uses a 100 ms local-storage timer and silently ignores write failures. A stale draft can recover only instruction text in a modal. Metadata and supporting-file edits lack a merge path. The app guards route changes and handles Ctrl+S, but native close/restart and storage failure are separate cases. The saved output preview and draft output preview use the same name but different data paths. Provider format options remain available even where nothing is installed, and fallback paths can imply a deployment that was never selected.

**Design.** Put title, activation scope and save state in one persistent header. Use **Write / Preview** near the editor, and put provider output beside deployment options. Make local save and deployment explicit, especially on create or clone. Provide a file tree and one active file on desktop. On narrow widths switch between file list and editor with a deterministic Back action. Show validation beside each input, retain all stale draft fields for comparison, and surface a local draft failure. Give output preview separate **Generated format** and **Actual destination** labels, with read-only code and a reliable Copy response. [Editor form and draft validation](src/SkillSync.Daemon/wwwroot/js/components/skillEditor.js#L46), [draft recovery and save](src/SkillSync.Daemon/wwwroot/js/components/skillEditor.js#L150), [provider preview](src/SkillSync.Daemon/wwwroot/js/components/transpilerPreview.js#L5).

### Explore, Local Catalog and import review

**Layout.** Source, topic and search are vertically separated from the top-level import action. The wide split uses one page scroll. A long preview can carry the result list offscreen. The empty preview card announces a second instruction when the obvious affordance is a result row. The list repeats title, summary and repository, then the preview repeats them with path, license and revision. At 480 × 600 the layout becomes a route-like detail, which is appropriate, but the top shell still consumes the same height and the review replaces its loading heading, which can drop keyboard focus.

**Interaction.** Search and source changes reset selection. Topic changes can briefly render stale or empty results during an active fetch. On narrow, Back restores a result button only if that old element is still attached. Wide has no matching Back affordance. “Already in library” has no jump to the installed copy. Search failures and empty results offer retry or generic guidance without directly clearing the active topic. The Direct Import dialog accepts link and file together and silently prioritizes the file. Clicking Review closes the dialog before the review is ready. Returning after failure may mean entering the source again.

**Review.** Save as, provider choices and Import skill are beneath the full Markdown and supporting files. A long skill pushes the decision several screens down. No deploy target checked defaults to a local copy, which is sensible but implicit. The 15-minute plan expiry and capacity eviction are handled only as server failure. A collision just suggests a “-copy” slug, which can collide in turn. Files excluded from review are hidden in the file disclosure. License is a short string and can mean a repository file was merely found. A slow apply disables its own button but list, topic, source and Back can still replace the review; a late success can navigate to a skill from an earlier selection. Global route guards protect some navigation while the local Explore controls remain separate.

**Design.** Maintain a compact query strip and independent result/preview scrolling at desktop. Use list → review → result with Back restoring focus and scroll on narrow. Add **Open existing skill** for duplicates. Put a sticky review footer on both layouts with **Add to My Skills** and a visibly optional deploy choice. Show source, pinned revision, license status, collision and excluded-file count before the document. A real explicit replacement flow belongs in a later step. Switch link/file modes explicitly and retain input for retry. Make pending apply state authoritative across all Explore controls, with completion tied to the same review ID. Preserve the existing abort and generation checks. [Explore list and state](src/SkillSync.Daemon/wwwroot/js/components/explore.js#L61), [preview and import controls](src/SkillSync.Daemon/wwwroot/js/components/explore.js#L115), [server import review](src/SkillSync.Daemon/Core/Engine/SkillImporterService.Plans.cs#L121).

### Settings, Connections, Diagnostics and trash

**Connections.** The live account includes registered Gemini CLI, Antigravity and Codex, plus unavailable clients. Each client occupies a separate bordered panel with display name, registration state, raw config path, controls and sometimes a skills root. Gemini CLI and Antigravity can repeat the same primary skill path even though the Antigravity mirror is different. “Registered” confirms a config record. It leaves connection health, client restart and actual projection state unclear. A disabled Connect beside an undetected client has little next-step guidance. The instructional restart line and success toast repeat the action, but the result disappears and the page does not show whether a restart is still needed.

**Appearance & Startup.** The selection and binding defect is documented in section 2. A full-width theme dropdown in a largely empty card looks like an immediate app preference. The actual Save action lives in the next card. Busy and success states lack an explicit summary of which values changed. Startup feedback also needs to distinguish registry-registration errors from window behavior and theme preview.

**Diagnostics.** “N watched roots” is a technical counter with little assurance about real provider health. Reconcile is a single button whose scope and safe behavior are unclear. The summary reports conflicts and failed destinations but omits missing destinations and the operation time or a direct review link. The log presents raw text, repeats identical path fragments, and lacks kind filters, grouping, actionable links or refresh on every relevant event while open. Recent activity can tell the same story as the backup list without helping resolve it. Trash presents a slug and Restore, without deletion time, origin, destination preview, search, or a visible link back to the recovered row. Conflict and trash actions use confirmations, but the restored copy or skill immediately leaves the user in Reader and can erase their place in Diagnostics.

**Design.** Use one settings navigation surface with compact grouped rows. Connections should show **Detected / Registered / Restart required / Unavailable**, with exact paths and backup details collapsed. ## 6. Implementation order and release gates

1. **P0 — Settings integrity.** Fix the input contract, require explicit preference fields, decouple theme from startup/tray, and remove silent cross-setting mutation. Add native and HTTP contract tests before deploying.
2. **P1 — Conflict comprehension and resolution.** Introduce reason-coded issue records, per-destination state and hash-checked comparison. Build Reader Review, Diagnostics queue and verified mirror recognition. Keep a safe state transition for foreign files, differing files, missing files and failed writes. Verify that the four real matching bundles would produce a no-write comparison while the bootstrap remains a separate case.
3. **P1 — Shell and Library.** Simplify counts and status badges, make row issue actions direct, separate scope/query/filter semantics, keep focus and scroll through navigation and SSE, and define provider readiness language.
4. **P2 — Reading, editing and import.** Give each work area a stable action region, explicit local-versus-deploy semantics, easy supporting-file review, predictable Back and visible recovery. Preserve staged imports and prevent stale results from taking over the current selection.
5. **P2 — Settings and diagnostics finish.** Reduce panels, distinguish detected from registered and healthy, add actionable operation history and reversible outcomes, and validate logs/paths for privacy before any export.
